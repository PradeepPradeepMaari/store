# Store Order & Inventory Management System

A fully-functional RESTful API built with **Laravel 10** and **MySQL** for managing store orders, products, customers, and inventory. Implements concurrency-safe stock management, queued order confirmation, and comprehensive automated testing.

## Project Overview

This application is a backend-only Laravel API that manages:
- **Products** with stock, pricing, and tax information
- **Customers** identified by unique email
- **Orders** with automatic subtotal, tax, and grand-total calculations
- **Stock deduction** with race-condition prevention using database-level locks
- **Order confirmation** via a queued background job

---

## Features

- ✅ RESTful JSON API (3 endpoints)
- ✅ Create orders with automatic tax & total calculations
- ✅ Find-or-create customer by email
- ✅ Concurrency-safe stock deduction (lockForUpdate + atomic decrement)
- ✅ Duplicate product ID consolidation within an order
- ✅ Historical price and tax snapshots in order items
- ✅ Customer order history with eager loading (no N+1)
- ✅ Low-stock products with configurable threshold
- ✅ Queued order confirmation job with afterCommit()
- ✅ Full transaction rollback on any failure
- ✅ 46 automated tests (Unit + Feature) — all passing
- ✅ Form Request validation with detailed error messages
- ✅ API Resources for clean, consistent JSON responses

## Queue Worker Instructions

```powershell
# Or process a single batch

php artisan queue:failed

# Retry a failed job by ID
php artisan queue:retry {id}
```

**Note:** In the `testing` environment, `QUEUE_CONNECTION=sync` is set in `phpunit.xml`, so jobs run inline during tests without needing a worker.

```json
      "quantity": 2

      "product_id": 2,
      "quantity": 1
```

## Architecture and Design Decisions

### 1. Thin Controllers, Fat Services
All business logic lives in `App\Services\OrderService`. Controllers handle HTTP concerns only (parse request, call service, format response). This makes logic testable independently of the HTTP layer.

### 2. Concurrency Safety
The `OrderService::createOrder()` method uses:
```php
Product::whereIn('id', $productIds)
    ->orderBy('id')           // consistent ascending lock order
    ->lockForUpdate()
    ->get();
```
- **Consistent lock ordering**: Products are always locked in ascending ID order, eliminating the "lock inversion" deadlock scenario where Transaction A locks product 1 then tries 2, while Transaction B locks product 2 then tries 1.
- **Validation inside the lock**: Stock check happens after `lockForUpdate()` — a concurrent transaction blocks at the lock boundary and sees the already-decremented value.
- **Atomic decrement**: `Product::where('id', $id)->decrement('stock_quantity', $qty)` is a single SQL `UPDATE` statement.

### 3. bcmath for Financial Calculations
PHP floats lose precision (`0.1 + 0.2 !== 0.3`). All monetary arithmetic uses `bcmath` (`bcmul`, `bcadd`, `bcdiv`) with 4 decimal places of intermediate precision, rounded to 2 for storage.

### 4. Historical Price Snapshots
`unit_price` and `tax_percentage` are copied from the product into each `order_item` row at order creation time. This ensures that if a product's price changes later, historical orders remain accurate.

### 5. afterCommit() Job Dispatch
```php
SendOrderConfirmationJob::dispatch($order->id)->afterCommit();
```
This tells Laravel to only push the job onto the queue **after the database transaction commits successfully**. If the transaction rolls back (e.g., stock check fails), the job is never dispatched.

### 6. Duplicate Product ID Handling
Before processing, items are consolidated:
```php
collect($items)->groupBy('product_id')->map(fn($g) => $g->sum('quantity'))
```
This ensures that `[{product_id:1, qty:3}, {product_id:1, qty:4}]` becomes `{1: 7}`, resulting in a single `order_item` row and a single stock deduction of 7.

### 7. API Resources
All endpoints return data through dedicated `JsonResource` classes. `whenLoaded()` is used throughout to prevent N+1 queries while keeping resources reusable.

### 8. Form Request Validation
All three endpoints use dedicated `FormRequest` classes with custom validation messages. Laravel automatically returns HTTP 422 with JSON errors when `postJson` or `Accept: application/json` is set.

## Assumptions Made

1. **Tax is per-product**: Each product has its own `tax_percentage`. There is no global tax rate.
2. **Tax is calculated on subtotal**: `tax_amount = (unit_price × quantity) × tax_percentage / 100`
3. **Customer name is preserved on re-use**: When a customer exists by email, `firstOrCreate` keeps their existing name (the provided name in the request is only used for new customers).
4. **Currency**: All monetary values are in a single currency (no multi-currency support).
5. **No authentication**: The APIs are public. In production, these would be protected by Sanctum or similar.
6. **Low-stock "strictly less than"**: A product with `stock_quantity = 10` and `threshold = 10` is NOT considered low-stock.
7. **Products ordered by stock then name**: The low-stock endpoint returns products ordered by `stock_quantity ASC`, then `name ASC` for consistency.

---

## Known Limitations

1. **No true concurrent test**: Testing true race conditions requires spawning separate OS processes with independent database connections, which is complex in a standard PHPUnit suite. The implementation is demonstrably correct via `lockForUpdate()`, but the test validates the business logic sequentially.
2. **SMTP not configured**: Order confirmation is logged (not emailed). A real SMTP driver would require `MAIL_MAILER=smtp` with valid credentials.
3. **No pagination**: The customer order history and low-stock endpoints return all records. For large datasets, pagination should be added.
4. **No soft deletes**: Products and customers cannot be soft-deleted; referential integrity constraints prevent deleting products referenced in orders.
